日期：2026-10-15。远程入口：`ssh -p 43573 root@connect.westd.seetacloud.com`。

本方案区分代码机制与实验因果；下列优化均未证明能提升胜率。先核对远端实际版本、运行参数、数据和权重，再决定实验。已有作业和生产权重保持运行，实验使用独立产物路径。

## 第一项实验：策略权重

当前策略加权定义为 `max(0, z - V)`，全批权重为零时回退为等权。失败标签为 -1，但价值头没有输出范围约束，不能断言所有失败行都必然被过滤。

用采集起点模型对对应数据分块前向，分别统计胜/负样本数量、非零权重比例、权重和、价值预测范围和有效样本量 `(sum(w))² / sum(w²)`。报告 eval 模式诊断与实际训练 dropout/逐批回退机制的差别。

若资源允许，以相同起点、数据、划分、训练 seed、轮数、学习率和设备比较 `pi_weight=advantage` 与 `none`。两臂都必须重新训练，不能把历史候选与新训练候选的差异直接归因于权重开关。初筛结果不能代替多 seed 复验。

## 后续独立实验

1. **种子轮换**：每轮更换不与评估段重叠的开局 seed 段。只改变开局分布；保持场数和训练预算一致。恢复运行时必须能恢复轮次与 seed 段映射。
2. **探索实现**：验证子树提升为新根后补加噪声，以及 epsilon 动作不被后续选择覆盖。每项单独测试；当前 epsilon 为零时，后者不解释现有平台。
3. **回放**：比较本轮数据与近期数据混合。固定优化步数和采样量，避免把更多训练量误判为回放效果；按场/种子划分防止跨轮相似轨迹泄漏到验证集。
4. **表示与辅助任务**：只有在搜索明显优于裸网、训练信号和覆盖问题已排查后，再比较牌堆非线性集合编码或辅助胜负预测头。第一轮保留现有搜索回报，避免同时改变任务目标和架构。

## 不作为已证实结论的建议

- 当前牌堆分别做均值池化，张数另作为标量输入；增加 sum 不等于补回此前完全缺失的数量信息。
- 当前全局输入已含能量、血量、状态等特征；架构实验应测试交互表达方式，而不能声称这些信息此前不存在。
- 持续继承候选模型是训练链的明确设计。只有部署最佳模型与持续训练当前模型可以并存，门控不回滚不是必然错误。
- 三五轮回放、混合比例、增加容量及拆分价值头都属于待验证超参数或结构选择，不直接替换生产配置。
- 历史笔记中的优势加权收益和加深网络无效结果需要保留作参照；新实验只对其实际数据、预算和种子范围负责。

### 尾段窄批交给 CPU（采集吞吐，2026-10-16）

动机（实测，`apps/net-test` 单次前向）：**一次前向的耗时几乎与批宽无关** —— cuda 批 1 = 1.132 ms、
批 256 = 1.412 ms（kernel 派发受限）；cpu 批 1 = 0.403 ms、批 64 = 11.08 ms（近似线性）。
⇒ 尾段那种"1～5 行"的窄批在 GPU 上每行贵两个数量级，而 CPU 单会话在窄批上反而更快。
交叉点 ≈ 批 6（单会话）/ ≈ 10 行（4 会话）⇒ 默认门槛 `cpu_rows=10`。

- **形状**：一条 worker 线程领完自己那一场的活、任务表被领空之后，**就地**转成前向线程
  （懒建私享 CPU 会话），把队列里的窄批吃掉。没有"专职 CPU 线程"这条独立代码路径。
- **判据**：`cpuAllowed()`（任务表领空，单调）× `narrowReady()`（待服 ≤ `cpu_rows`）。
- ⚠️ **判据必须每次醒来重算（lambda），不能提前存成 `const bool`**：线上死锁的真因 —— 主设备线程
  算完 `narrow=true` 才睡下，醒来谓词还读那份过期值 ⇒ 队列涨宽它也不接手，worker 侧又因"不是窄批"
  不接手 ⇒ 两侧都不够格、谁也醒不来（33 条线程全 S、GPU 0%、13 min 零进展）。
  触发条件是"`cpu_rows` **低于**同时在飞的行数"⇒ 守卫若一律用 `--cpu-rows 10`（> K 棵树）
  永远跨不过这条边界。回归项：`--cpu-rows 2/3/5` 配 K=8 必须跑完。
- 实测（2016 场/轮，同一配方不同种子段）：

  | | R8（旧结构） | R9（收敛后） |
  |---|---|---|
  | 采集墙钟 | 843 s | **690 s** |
  | 前向调用 | 753,385 | 1,155,357 |
  | 其中 CPU 1 行/次 | 496,137（65.9%） | 930,574（80.6%） |
  | GPU 调用 | 257,248 | 224,783 |
  | 叶评估行数 | 43.0M | 45.7M |
  | ORT 前向 | 577.1 s | 338.9 s |

  ⇒ CPU 吃掉七到八成的**调用次数**，GPU 调用数降到 22~26 万，收益来自**减少 GPU 调用次数**。
  ⚠️ 两轮种子段不同（33297632 vs 94483008）⇒ 跨种子墙钟**不能当因果**。
- **旧账复核（把 R8/R9 的 1.7× 差异追到底，判据 = 每轮日志的 `ORT 前向`)：**

  | 轮 | GPU 侧形状 | GPU 调用 | GPU 行 | 行/次 | ORT ms/次 | ORT µs/行 |

  | r1 | 纯 GPU | 2,158,521 | 60.7M | 28.1 | 1.052 | 37.4 |
  | r2 | 纯 GPU | 1,055,179 | 44.1M | 41.8 | 1.029 | 24.6 |
  | r3 | CPU×4 专职 | 283,574 | 40.6M | 143.3 | 1.614 | 11.3 |

  ⇒ **离群的是 r8，不是 r9 快**：同样 ~160 行/次、同一份代码路径（r5/r6/r7/r8），
  每次调用 1.29 / 1.33 / 1.47 / **2.24** ms —— 相邻轮次之间就能跳 1.7×，

  口径提醒：日志里的"均批"包了 CPU 那侧（刻意 1 行/次），**GPU 侧均批**才是关键（R8 = 165）。
